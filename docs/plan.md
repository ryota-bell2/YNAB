## 1. この計画書の目的

本計画書は、要件定義書に記載されたM0からM3までの開発を、3人で進めるための実行計画である。

最初から全仕様を固定せず、各マイルストーン開始前に対象ストーリーの受け入れ条件、画面、データ構造、エラーケースを具体化する。未着手部分は粗いまま管理し、週次のバックログ確認で更新する。

## 2. プロダクト概要

### 2.1 目的

同棲中または結婚初期で、家計ルールが固まっていない二人が、収入差を考慮した按分ルールによって共同家計を管理できるWebアプリを作る。

### 2.2 想定ユーザー

- 20代から30代のパートナー世帯
- 単純な折半では不公平感がある
- 家計管理や予算管理で挫折した経験がある
- 結婚、引っ越し、出産、車などの目標に向けて貯蓄したい
- 片方が家計管理を主導し、もう片方は受動的な場合も想定する

### 2.3 MVPに含める機能

1. メールアドレスとパスワードによる認証
2. パートナー招待とペアリング
3. 収入比率に応じた按分ルール設定
4. 支出の共通・個人タグ付け
5. カテゴリの作成・編集
6. カテゴリ別の月次予算割り当て
7. 支出入力
8. 月次の予算対実績表示
9. ログアウトとセッション管理
10. RLSによるデータアクセス制御

### 2.4 MVPに含めない機能

- 通知機能
- Google OAuth。余裕がある場合のみ追加候補とする
- 銀行口座やクレジットカードとの自動連携
- 大規模アクセスを前提とした構成
- 主導者と受動的パートナーで機能を分ける仕組み

## 3. 技術方針

- フロントエンド: Next.js App Router、TypeScript、Tailwind CSS
- バックエンド: Next.js Route Handlers または Server Actions
- DB・認証: Supabase PostgreSQL、Supabase Auth
- DBアクセス: M0中にSupabase公式クライアントとPrismaを比較し、採用方式を決定
- グラフ: Recharts
- ホスティング: Vercel
- ソース管理: GitHub
- ブランチ: `main` と `feature/機能名`
- マージ: Pull Request必須、他メンバー1人以上の承認後にマージ

### 4.2 現在のブロッカー

`app/page.tsx` からSupabaseクライアントを読み込む際、次のエラーが発生している。

```text
Module not found: Can't resolve '../lib/supabase/client'
```

最初に実際の配置を確認し、次のいずれかに統一する。

```text
ynab/
├─ app/
│  └─ page.tsx
└─ lib/
   └─ supabase/
      └─ client.ts
```

この場合のimport例:

```ts
import { supabase } from "@/lib/supabase/client";
```

`tsconfig.json` の `@/*` が `./*` を指していることも確認する。

## 12. リスクと対応

| リスク | 影響 | 対応 |
|---|---|---|
| 各自の作業時間が不足 | 日程遅延 | 週次工数を先に共有し、MVP外機能を追加しない |
| Supabase・RLSの学習コスト | M1以降が停止 | M0で2ユーザーの最小検証を完了し、手順を残す |
| Prismaの導入が複雑 | DB開発が遅れる | M0で判断期限を設け、難しい場合はSupabase公式クライアントを採用 |
| 仕様を細かく決めすぎる | 実装開始が遅れる | 着手対象だけ受け入れ条件を詳細化する |
| 個人支出が相手に漏れる | 重大な信頼・セキュリティ問題 | UI制御だけでなくRLSと複数ユーザーテストで担保する |
| 秘密情報の漏洩 | 不正アクセス | GitHubと公開Notionに秘密を置かず、漏洩時は即時ローテーションする |
| 1人に知識が集中 | 作業停止 | PRレビュー、ペア作業、Notionへの決定記録を行う |
